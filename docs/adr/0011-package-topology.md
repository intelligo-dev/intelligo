# ADR-0011: One package per runtime target; shared types are subpaths

**Status:** Accepted
**Date:** 2026-09-12
**Supersedes:** the public allowlist and the evolution map in [ADR-0006](0006-package-allowlist.md). ADR-0006's private list and its three rules stand.
**Driver:** an open-source framework for developers who did not write it has to have a package layout they can predict.

## Context

Thirteen packages were published, and three of them had no rule behind
them. `money` (277 lines, one file) was imported by nothing — its stated
reason, that `executions/pricing` needed its types, was a refactor that
had not happened. `http` (148 lines) had one consumer, `auth`, and
existed to hold a 26-line Next.js binding. `billing-core` (904 lines)
was never imported without `billing`, and `billing/plans` and
`billing/payment` were already re-export shims back into it. No ADR
covered any of the three, and ADR-0006's allowlist named packages that
do not exist (`database`, `workspaces`, `entitlements`, `credits`,
`billing-stripe`, `next`) and a file that does not exist
(`config/public-packages.json`).

The page registry sat outside every workspace: not in turbo, not linted
by `pnpm lint`, its 15k lines never type-checked in place, its
`requires.json` hand-copied into the CLI. The reason was a rule this
repository had made for itself — everything under `packages/` ships to
npm — not anything the Turborepo convention asks for, which keeps
private tooling workspaces (`packages/eslint-config`,
`packages/typescript-config`) under `packages/`.

## Decision

**A separate package exists only when it has its own peer dependency,
runtime target or adapter. Shared pure-TypeScript modules are subpath
exports of the package that owns the concept.** This is the rule
Better-Auth (`better-auth/next-js`, `better-auth/react`), Clerk
(`@clerk/nextjs`, `@clerk/backend`), Payload (`@payloadcms/next`,
`@payloadcms/db-postgres`), the AI SDK (`ai`, `@ai-sdk/react`,
`@ai-sdk/openai`) and Sentry (`@sentry/core`, `@sentry/nextjs`) all
follow, and it is the one a developer arriving from any of them
expects.

Applied:

| Was                           | Is                                                                 | Why                                                                          |
| ----------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `@intelligo-dev/money`        | `@intelligo-dev/core/money`                                        | A dependency-free subpath is reachable from a leaf as well as a package is.  |
| `@intelligo-dev/http`         | `@intelligo-dev/core/request-context` + `@intelligo-dev/next`      | The contract imports nothing; the binding is the one `next/*` importer.      |
| `@intelligo-dev/auth/next`    | `@intelligo-dev/next/auth`                                         | One package owns every `next/*` import; `auth` imports only authentication.  |
| `@intelligo-dev/billing-core` | `@intelligo-dev/billing/{plans,plan-registry,payment,quota-types}` | Subpaths that reach neither Stripe nor `server-only`, asserted on the files. |
| `registry/`                   | `packages/registry`, `@intelligo-dev/registry`, `private: true`    | A workspace the toolchain owns; never published (ADR-0002, ADR-0010).        |

`mastra` stays: it has its own optional peer. `audit` and `jobs` stay
this round; they own tables (ADR-0004) and the fold was not asked for.
`ui` is legacy, used by `admin`, and not part of the page contract.

The published set is therefore `core`, `auth`, `billing`, `executions`,
`audit`, `jobs`, `admin`, `cli`, `next`, `mastra`, `chat` (ADR-0012),
plus legacy `ui`. The graph:

```
core ← auth ← next
core ← audit ← executions ← mastra
core ← jobs
core ← billing (← executions)
core, auth, audit, executions, jobs, ui ← admin
core, auth, billing, executions ← chat
cli imports nothing
```

### The registry as a workspace

`packages/registry` carries `build` (shadcn), `lint` and `type-check`.
Type-checking resolves every shipped target to the item's own source
and only shadcn primitives and scaffold-provided files to the reference
app, so an item is checked against what it ships, not against a copy
of it. The CLI's bundled `requires.json` is generated by the CLI build;
the site's sync is a turbo task downstream of the registry build. The
rules that assumed everything under `packages/` is published now read
`private`, as `pnpm publish -r` always did, and a private workspace
under `packages/` must say "never published" in its README.

## Consequences

- Three npm names are deprecated with a pointer to the new path;
  nothing is unpublished. `tests/architecture/dependency-direction.test.ts`
  refuses the old names and says where the code went; so does ESLint.
- The leaf property each fold relied on is asserted on the files:
  `core/money` imports nothing, `core/request-context` imports only
  `core/registry`, and the four billing subpaths reach only
  `core/registry` when their relative imports are walked.
- `tests/architecture/peer-policy.test.ts`'s one-door rule now names
  `packages/next/src/`; no other package's source may import `next/*`.
- A future fold or split is judged by the rule above, not by taste. A
  Stripe adapter package appears when a second payment provider does.
